# jooq-rules

**jOOQ を ORM ではなく、型安全な SQL DSL として使う。**

Kotlin/Spring 向けの規約集。「禁止」ではなく「既定値と例外」として書き、
それぞれの規則に *なぜ* と *どんなときは違うのか* を添えた。

[English](README.md) · [한국어](README.ko.md) · [日本語](README.ja.md)

</div>

> jOOQ は SQL を隠すための道具ではなく、SQL を**コンパイル時に検証できるようにする**ための道具だ。
> この区別が、ここにあるすべての規則の根にある。

[Claude Code](https://claude.com/claude-code) のスキルとしても、ただ読む文書としても使える。

## この規約の出どころ

**個人プロジェクトで jOOQ を使いながらまとめたもので、大規模な本番トラフィックで検証したものではない。**
確立された標準ではなく、一人の開発者の判断の記録として読んでほしい。

根拠として挙げた失敗のかたち — コネクションプールの枯渇、OFFSET のスキャン量増加、静かなデータ不整合 —
はバックエンド一般の問題であって、jOOQ 固有のものではない。jOOQ 固有なのは
**それらを避けられる場所がライブラリのどこにあるか**であり、この文書が扱うのはそこだ。

## この文書の違い

jOOQ の公式ドキュメントは API をよく説明している。抜けているのは **いつ何を選ぶか** で、
実務で詰まるのはたいていそこだ。

### 禁止ではなく、既定値と例外

多くの規約文書は「X をするな」で終わる。すると X が正しい場面に出会ったとき、規則を破るか、
不自然に迂回することになる。

ここでは規則ごとに既定値を決め、**その既定値が当てはまらない条件**も併記する。

```
selectFrom は禁止ではない。ただ、ほとんどの読み取りでは projection のほうが良いので、
既定値を projection にしている。

判断基準は一行:「このクエリが読んでいるのに使わない列はあるか?」
あるなら projection。ないなら selectFrom で構わない —
全列を並べるのは、同じことを長く言っているだけだ。
```

plain SQL の式も同じ扱いだ。**スキーマ識別子を文字列で書くこと**と、**式を plain SQL で書くこと**
は別の行為である。前者は避けるが、`ts_rank` や JSON 演算子のように codegen が表現できない後者は
**正当な逃げ道**として認める。ただしバインド変数を使い、一箇所にまとめることを条件とする。

### トレードオフの代償を書く

「カーソルページネーションを使え」と書かれた記事は多い。**カーソルにすると何を失うのか**まで
書かれた記事は少ない。

```
カーソルの代償: 前後への順次移動しかできない。
「N ページへジャンプ」と「全部で何ページか」を捨てることが、カーソルを選ぶトレードオフだ。

無限スクロールや「もっと見る」の UI なら、そもそもその機能は要らないのでカーソルが合う。
ページ番号が並ぶ管理画面のテーブルなら OFFSET が合う。
先に UI の要件を確認してから選ぶ。
```

`MULTISET` も同じだ。1 クエリで済み型安全も保てるという利点は明確だが、既定値は `batch fetch`
のままにする — 往復コストが**実際に測定されたあとで**切り替える。
「1 クエリで書けるとかっこいい」は導入の根拠にならない。

## 規則のいくつか

**プロジェクションは性能最適化である前に契約だ。**
どの列を読むかがコードに書かれていれば、そのクエリが何に依存しているかは読むだけで分かる。

**エンティティに nullable な集計フィールドを差し込まない。**
埋まった経路と埋まらなかった経路を呼び出し側が区別できないなら、**それは型が嘘をついている**。
集計や結合の結果には、読み取り専用のプロジェクション型を別に用意する。

**Adapter は DB が言ったことをそのまま運ぶ。解釈はドメインがする。**
Adapter で `?: ""` として NULL を埋めると、「まだ来ていない」と「失敗した」が一つに潰れる。
その二つを区別しなければならない画面は、そこから分岐できなくなる。

**マッパーは private であるべきだ。**
public にすると、他の Adapter や UseCase が Record を直接変換しはじめる。すると
フィールドを一つ足すたびに「変換ロジックはどことどこにあったか」を探し回ることになる。

**抽象化の判定基準:「この関数を読んで、実行される SQL を思い描けるか?」**
描けないなら隠しすぎだ。jOOQ の上にもう一度 ORM を載せない。

**外部呼び出しはトランザクションの外で行う。**
外部 API が遅くなると、その時間だけ DB コネクションが握られ、やがてプールが枯れる。
トランザクションの中では**意図だけを記録**し（Outbox）、発行はワーカーが行う。

**外部に渡すカーソルには署名する。**
ソートキーの値をそのまま出すと、クライアントが改竄して他のユーザーの範囲を辿れてしまう。
呼び出し元の識別子とフィルタ条件をカーソルに封じ込め、復号時に突き合わせる。

## 前提と限界

- 例は **Kotlin + Spring Boot + PostgreSQL** を前提にしている。Java や他の DB なら構文を変えるだけでいい
- §6 のマッピング境界はヘキサゴナル（ポート・アダプター）構成を前提にしている。その構成を使わないなら、その節は合わない
- `MULTISET` は jOOQ 3.15 以降の機能だ
- **チームの規約があるなら、チームのものが勝つ。** これは一個人の規約であって標準ではない
- 大規模運用ではなく個人プロジェクトから出てきたものだ — [この規約の出どころ](#この規約の出どころ)を参照
